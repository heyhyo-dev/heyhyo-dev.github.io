### HTTP  
비유: 택배 회사 트럭 (운송 수단)  
우리가 인터넷을 할 때 쓰는 가장 기본적인 **'길'**이자 **'운송 수단'**이다.  
웹 브라우저 주소창에 http://라고 쓰는 게 "이 택배 트럭을 이용해서 데이터를 가져와!"라는 뜻이다.  
`예시`  
    ◦ 친구가 편지를 보낼 때 **'우체국'**이라는 시스템을 이용하듯, 인터넷상의 컴퓨터끼리 데이터를 주고받을 때 쓰는 가장 기초적인 통신 규칙이다.  
    ◦ "요청(Request)"과 "응답(Response)" 두 가지로 이루어져 있다. (주문하면 -> 음식이 나온다.)  
`ABAP 개발자용 설명` 
    ◦ SAP 시스템끼리 통신할 때 **RFC(Remote Function Call)**를 쓴다.  
    ◦ HTTP는 **"웹 세상의 RFC"**라고 보면 된다.  
    ◦ RFC가 SAP 전용 도로라면, HTTP는 전 세계 모든 컴퓨터가 다니는 공용 도로.  
    -> Gateway는 이 HTTP 도로를 통해 들어오는 요청을 받아서 처리하는 역할.

### RESTful
비유: "동사"가 아닌 "명사" 위주의 식당 주문법   
RESTful은 기술 이름이라기보다, **"웹 서비스를 촌스럽지 않고 세련되게 만드는 설계 스타일(유행)". 예전 방식(SOAP)은 복잡했는데, RESTful은 아주 단순하고 직관적.  
`예시`  
    ◦ 옛날 방식 (SOAP): 식당에 가서 "김밥_만들어주세요", "김밥_삭제해주세요"처럼 주문 내용마다 말이 다 달랐음.  
    ◦ RESTful 방식: 메뉴판에 "김밥(자원)" 딱 하나만 있음. 그리고 손님은 4가지 동작만 할 수 있음. (주세요, 추가해주세요, 고쳐주세요, 치워주세요).  
    ◦ 즉, **"자원(명사)"**을 정해두고, **"동작(동사)"**은 딱 4개로 통일한 아주 심플한 방식입니다.  
`ABAP 개발자용 설명` (Function vs Table)  
    ◦ Function Module 방식 (옛날): Z_CREATE_CUSTOMER, Z_GET_CUSTOMER, Z_DELETE_CUSTOMER... 펑션 이름을 동작마다 다 따로 만들었죠? 이게 옛날 스타일(SOAP)에 가깝습니다.    
    ◦ RESTful 방식: 그냥 **CUSTOMER**라는 이름(자원/URI) 하나만 둡니다. 그리고 HTTP 명령어(Method)에 따라 ABAP의 SQL 동작을 매핑합니다.  
    

|HTTP 메소드 (웹)|ABAP SQL (데이터베이스)|의미|
|------|---|---|
|GET|SELECT|조회 (보여줘)|
|POST|INSERT (or MODIFY)|생성 (만들어줘)|
|PUT/PATCH|UPDATE|수정 (고쳐줘)|
|DELETE|DELETE|삭제 (지워줘)|

핵심: "펑션 이름 뭘로 짓지?" 고민할 필요 없이, **"어떤 테이블(자원)을 건드릴까?"**만 생각하고 
동작은 SELECT, INSERT, UPDATE, DELETE 4개 중에 고르는 방식이 바로 RESTful.
